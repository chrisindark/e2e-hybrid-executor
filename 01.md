## 1. Executive Summary & Deliverable Scope

The objective of this deliverable is to transition the monolithic, single-tenant, SQLite-backed prototype into an enterprise-grade multi-tenant foundation. This document details the exact configuration, schemas, and patterns for:

1. **Monorepo Topology:** Migration to `pnpm` workspaces + Turborepo, establishing boundary isolation between four deployable services (`gateway-api`, `runner-e2e`, `runner-api`, `ai-service`) and reusable core packages.
2. **PostgreSQL Multi-Tenancy & Row-Level Security (RLS):** Strict data isolation enforced at the database kernel level using PostgreSQL RLS, automated session parameter injection (`SET LOCAL app.tenant_id`), and migrations.
3. **Async Context Propagation:** Propagation of `tenantId`, `actorId`, and correlation identifiers across asynchronous boundaries via Node.js `AsyncLocalStorage` and BullMQ job envelopes.
4. **Data Contract (`TestSpec v1`):** Complete canonical Zod schemas for deterministic UI/API execution steps, locator fallback ladders, variable interpolation, and immutable versioning entities.

## 2. Monorepo Architecture & Workspace Configuration

The repository is structured as a pnpm monorepo managed by Turborepo to enforce dependency boundaries and cache build outputs.

### 2.1 Workspace Layout

```

├── services/
│   ├── runner-e2e/              # Playwright browser worker (ephemeral chromium contexts)
│   ├── runner-api/              # HTTP-only runner (lightweight, zero-browser API testing)
│   ├── ai-service/              # Authoring, recovery, agentic-primary, evals
│   └── scheduler/               # Cron suites, scheduled triggers, fan-out coordinator
├── packages/

├── pnpm-workspace.yaml
├── package.json
├── turbo.json
└── tsconfig.base.json
```

### 2.2 Boundary Isolation Rules

1. **Zero Direct Import Rule:** `services/runner-e2e`, `services/runner-api`, and `services/ai-service` must NEVER directly import each other. All inter-service data exchanges must conform strictly to `packages/contracts`.
2. **Worker Purity:** Workers (`runner-e2e`, `runner-api`) never serve external HTTP traffic. They consume jobs exclusively from Redis queues and report status events via Redis Streams.
3. **Database Access Restriction:** Only `apps/gateway-api` and `packages/db` execute DDL migrations. Microservices access the database strictly through tenant-scoped repositories or RPC/events.

## 3. PostgreSQL Multi-Tenancy & Row-Level Security (RLS)

Every tenant's data resides in a single, shared PostgreSQL database. Isolation is enforced at the database engine level via PostgreSQL Row-Level Security (RLS) policies. Application code never relies on manual `WHERE tenant_id = :tenantId` filtering for security.

### 3.1 PostgreSQL Kernel Isolation Architecture

```
                      Client Request (Bearer JWT)
                                  │
                                  ▼
                     ┌───────────────────────────┐
                     │ apps/gateway-api          │
                     │ TenantContextMiddleware   │
                     │ Sets: tenantId in ALS     │
                     └─────────────┬─────────────┘
                                   │
                                   ▼
                     ┌───────────────────────────┐
                     │ packages/db               │
                     │ Transactional Runner      │
                     │ BEGIN;                    │
                     │ SET LOCAL app.tenant_id..;│
                     └─────────────┬─────────────┘
                                   │
                                   ▼
             ┌───────────────────────────────────────────┐
             │ PostgreSQL 16 Engine                      │
             │ Current Setting: app.tenant_id = 'org_123'│
             │                                           │
             │  ┌──────────────────────────────────────┐ │
             │  │ Row-Level Security (RLS) Filter      │ │
             │  │ tenant_id = current_setting(...)     │ │
             │  └──────────────────────────────────────┘ │
             │                                           │
             │ [Tenant A Rows]     [Tenant B Rows (BLOCKED)]
             └───────────────────────────────────────────┘
```

### 3.3 Database Client Transaction Helper (`packages/db/src/tenant-context.ts`)

```typescript
import { Pool, PoolClient } from 'pg';

export class TenantDatabaseClient {
  constructor(private readonly pool: Pool) {}

  /**
   * Executes a database operation wrapped in a tenant-isolated transaction.
   * Injects the tenantId into PostgreSQL session variables via SET LOCAL.
   */
  async withTenant<T>(
    tenantId: string,
    operation: (client: PoolClient) => Promise<T>,
  ): Promise<T> {
    const client = await this.pool.connect();
    try {
      await client.query('BEGIN');
      // Enforce tenant ID in current transaction scope
      await client.query('SELECT set_config($1, $2, true)', [
        'app.tenant_id',
        tenantId,
      ]);

      const result = await operation(client);

      await client.query('COMMIT');
      return result;
    } catch (error) {
      await client.query('ROLLBACK');
      throw error;
    } finally {
      client.release();
    }
  }

  /**
   * System-level operations (e.g. migrations or cron reconcilers) that bypass RLS.
   * Requires explicit admin role.
   */
  async withSystemAdmin<T>(
    operation: (client: PoolClient) => Promise<T>,
  ): Promise<T> {
    const client = await this.pool.connect();
    try {
      await client.query('BEGIN');
      await client.query("SET LOCAL ROLE 'platform_admin'");
      const result = await operation(client);
      await client.query('COMMIT');
      return result;
    } catch (error) {
      await client.query('ROLLBACK');
      throw error;
    } finally {
      client.release();
    }
  }
}
```

## 4. Request Context & AsyncLocalStorage (ALS)

In Node.js, context must not be passed manually down dozens of function parameters. We establish an `AsyncLocalStorage` store in `packages/telemetry` and populate it at the edge of the API and worker consumers.

### 4.1 Context Definition (`packages/telemetry/src/request-context.ts`)

```typescript
import { AsyncLocalStorage } from 'async_hooks';

export interface TenantContext {
  tenantId: string;
  actorId: string;
  actorType: 'user' | 'api_key' | 'system';
  traceId: string;
  planTier: 'free' | 'starter' | 'pro' | 'enterprise';
}

const storage = new AsyncLocalStorage<TenantContext>();

export const RequestContext = {
  run<T>(ctx: TenantContext, callback: () => T): T {
    return storage.run(ctx, callback);
  },

  get(): TenantContext {
    const ctx = storage.getStore();
    if (!ctx) {
      throw new Error(
        'Tenant context is not established in this asynchronous execution frame.',
      );
    }
    return ctx;
  },

  getOptional(): TenantContext | undefined {
    return storage.getStore();
  },

  getTenantId(): string {
    return this.get().tenantId;
  },
};
```

### 4.2 Gateway NestJS Middleware (`apps/gateway-api/src/common/middleware/tenant-context.middleware.ts`)

```typescript
import {
  Injectable,
  NestMiddleware,
  UnauthorizedException,
} from '@nestjs/common';
import { Request, Response, NextFunction } from 'express';
import { RequestContext, TenantContext } from '@repo/telemetry';
import { v4 as uuidv4 } from 'uuid';

@Injectable()
export class TenantContextMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction) {
    const traceId = (req.headers['x-request-id'] as string) || uuidv4();

    // AuthGuard populates req.user after JWT verification
    const user = (req as any).user;
    if (
      !user &&
      !req.path.startsWith('/health') &&
      !req.path.startsWith('/v1/auth')
    ) {
      return next(); // Let AuthGuard trigger 401
    }

    const context: TenantContext = {
      tenantId: user?.tenantId || 'anonymous',
      actorId: user?.sub || 'anonymous',
      actorType: user?.type || 'user',
      traceId,
      planTier: user?.planTier || 'free',
    };

    RequestContext.run(context, () => next());
  }
}
```

### 4.3 Worker Queue Envelope (`packages/queue/src/envelope.ts`)

When pushing jobs to BullMQ, the `tenantId` and metadata are serialized inside the envelope:

```typescript
export interface JobEnvelope<T> {
  payload: T;
  meta: {
    tenantId: string;
    actorId: string;
    traceId: string;
    enqueuedAt: string;
    priority: number;
    planTier: 'free' | 'starter' | 'pro' | 'enterprise';
  };
}

export function wrapJob<T>(payload: T, priority = 0): JobEnvelope<T> {
  const ctx = RequestContext.get();
  return {
    payload,
    meta: {
      tenantId: ctx.tenantId,
      actorId: ctx.actorId,
      traceId: ctx.traceId,
      enqueuedAt: new Date().toISOString(),
      priority,
      planTier: ctx.planTier,
    },
  };
}
```

## 6. Migration & Verification Strategy

### 6.1 Phased Execution Plan

1. **Step 1: Workspace Initialization:** Run `pnpm init` at the root, declare `pnpm-workspace.yaml`, and configure `turbo.json`. Move shared utilities into `packages/contracts`, `packages/telemetry`, and `packages/db`.
2. **Step 2: Spin Up Infrastructure:** Deploy PostgreSQL 16 and Redis 7 via Docker Compose.
3. **Step 3: Database Migration:** Apply `001_initial_schema.sql` via node-pg-migrate or TypeORM migration runner with RLS verified.
4. **Step 4: Repository Decoupling:** Re-point `apps/gateway-api` to consume `TenantDatabaseClient` with transactional RLS isolation.

### 6.2 Acceptance Tests (Verification Checklist)

| Test ID          | Objective               | Test Procedure                                                                                               | Expected Result                                                                                          |
| :--------------- | :---------------------- | :----------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------- |
| **TEST-RLS-01**  | Cross-Tenant Isolation  | Insert test records for `tenant_id = A`. Switch connection session to `app.tenant_id = B` and query `tests`. | Query returns 0 records.                                                                                 |
| **TEST-RLS-02**  | RLS Check Insertion     | Set `app.tenant_id = A`. Attempt to insert a row with `tenant_id = B`.                                       | PostgreSQL throws `new row violates row-level security policy` exception.                                |
| **TEST-ALS-01**  | Async Context Retention | Fire 50 concurrent requests through NestJS middleware to a delayed handler.                                  | Every log line and DB query preserves the exact corresponding `tenantId` without cross-request bleeding. |
| **TEST-SPEC-01** | TestSpec v1 Validation  | Validate generated UI and API steps with invalid types or missing `intent` locators.                         | Zod schema throws descriptive validation errors with zero type escape hatches.                           |
